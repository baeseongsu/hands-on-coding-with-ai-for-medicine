# 07. 코드가 아니라 스펙을 고친다

배우는 것

- 구현 중 알게 된 것을 코드가 아니라 스펙에 반영하기
- 스펙과 코드가 어긋나는 순간 명세가 죽음

## 프롬프트 1

구현하다 알게 된 것 하나를 반영시킵니다. 없으면 아래 예시를 씁니다.

```text
최소 화면에 데이터 출처와 비임상 용도 안내가 보이게 해라.
```

## 프롬프트 2

```text
방금 변경한 내용을 spec.md, plan.md, tasks.md, checklist.md 에 반영해라.
문서와 코드가 어긋난 채로 두지 마라.
```

## 프롬프트 3

```text
문서 4개와 현재 코드가 서로 일치하는지 다시 검사하고 결과를 보고해라.
```

## 프롬프트 4 (사람이 직접 확인한 뒤)

```text
specs/roadmap.md 에서 이 단계의 체크박스를 채워라.
이 브랜치를 커밋하고 main 으로 병합한 뒤 브랜치를 삭제해라.
```

---

## 무엇을 보아야 하는가

- 구현하다 보면 스펙이 틀렸거나 부족했다는 걸 알게 됨. 이때 두 갈래
  - 코드만 고침: 스펙과 코드가 어긋남. 3주 뒤의 자신은 왜 그렇게 되어 있는지 모름. 명세가 죽는 방식
  - 스펙을 고치고 코드를 맞춤: 스펙이 계속 진실
- 프롬프트 2가 이 파일의 목적
- `spec.md`가 실제로 갱신됐는지. 에이전트는 코드만 고치고 끝내려는 경향이 있음. 문서를 건너뛰면 다시 시킬 것
- `checklist.md`에 새 확인 항목이 생겼는지. 요구사항이 늘었으면 확인 항목도 늘어야 함
- `roadmap.md`의 체크박스가 채워졌는지

## 여기서 멈추고 확인

- [ ] `git diff`에 코드 변경과 문서 변경이 함께 있음
- [ ] `checklist.md`에 새 항목이 반영됨
- [ ] `roadmap.md`의 Phase 1이 완료로 표시됨
- [ ] 브랜치가 `main`에 병합됨

Phase 1 종료. 방금 한 것이 SDD 한 사이클 전체입니다.
