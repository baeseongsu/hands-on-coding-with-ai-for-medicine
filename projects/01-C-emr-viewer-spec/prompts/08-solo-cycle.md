# 08. 혼자 한 사이클

배우는 것

- 01~07을 안 보고 사이클을 돌릴 수 있는지
- 대상은 `specs/roadmap.md`의 Phase 2

## 순서

1. 다음 phase 찾고 브랜치. 에이전트가 질문하게 하고 `spec.md`
2. 모호한 곳 되묻기. `spec.md` 갱신
3. `plan.md`
4. `tasks.md` + `checklist.md`
5. 정합성 검사. 보고 읽고 내가 판단
6. 구현. 검증. 내가 직접 확인
7. 바뀐 게 있으면 문서에 반영. 병합

---

## 무엇을 보아야 하는가

- 프롬프트는 주지 않음. 막히면 01~07을 다시 열 것. 순서를 외우는 게 목적이 아님
- `roadmap.md`가 Phase 2에 원칙 1, 3, 5를 걸어 뒀음. 세 원칙이 한 단계에 걸리는 건 여기서 처음 join을 하기 때문
  - `diagnoses_icd`를 `d_icd_diagnoses`에 join할 때 코드와 버전을 함께 쓰는지. 코드만으로 join하면 화면은 정상인데 다른 진단이 붙음
  - join key를 추측하지 말고 데이터를 읽어 확인하게 할 것. 에이전트는 컬럼 이름이 같으면 관계라고 가정하는 경향이 있음
  - 검사 결과에서 단위가 값과 분리되지 않는지. 원칙 1이 여기서 걸림
  - 없는 설명이나 단위를 `null`이나 `undefined`로 노출하지 않는지, 반대로 없는 값을 만들어 채우지 않는지

## 여기서 멈추고 확인

- [ ] 에이전트가 파일을 쓰기 전에 질문함
- [ ] `spec.md`에 기술 선택이 없음
- [ ] `checklist.md`를 구현 전에 씀
- [ ] 진단이 코드와 버전을 함께 써서 join됨
- [ ] 검사 결과에 단위가 값과 함께 표시됨
- [ ] `roadmap.md`의 Phase 2가 완료로 표시됨

## 잘 안 됐다면

- 한 사이클을 완주하지 못해도 괜찮음. 어디서 막혔는지가 더 중요한 정보
- 에이전트가 질문 없이 진행함: 프롬프트에 "파일을 쓰기 전에 물어라"를 명시했는지 확인
- 스펙 쓰는 데 시간이 다 감: 범위를 줄일 것. 진단만 먼저 하고 처방과 검사를 나중에 해도 됨
- 구현이 스펙과 다르게 나옴: 스펙이 모호했던 것. 02번 파일의 교훈
